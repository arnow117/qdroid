### 用户场景与测试 *(必填)*

机器人应用开发者需要复用 Agent harness、Skills、MCP 与界面内容，同时在机器人主控上限制第三方软件能够访问的文件、网络、账号与设备能力。直接把第三方插件放进持有厂家控制权和账号凭据的进程，会让一个工具调用扩大为整机或账号访问；直接复用一个统一函数名，也可能掩盖不同设备的完成、取消与显示语义。

首期用户为拥有一台 Linux 机器人主控的个人开发者/操作者。操作者显式选择插件版本与授予权限；应用在受限环境使用被授予的能力；可信服务负责真实访问校验和结果观察。T1 Pro 是第一台待适配设备，同一业务应用应能先在 reference simulator 上验证契约。

期望结果：用户能在合格的 Linux 主控上安装固定版本应用，以明确授权调用少量能力，在 T1 原屏查看动态 Scene，并用语音或机身触摸切页；越权请求得到可解释的拒绝，不借此获得宿主、账号或机器人控制权限。

#### 用户故事 US-01 / US-02 — 授权插件的最小闭环（优先级：P1）

操作者选择固定插件并授予一个必要能力；开发者在 Linux 沙箱内调用 simulator，检查成功与越权拒绝。


**为何此优先级**：这是首个真实、可独立展示的运行结果，直接检查产品最重要的权限边界。

**独立测试**：无需设备、账号或模型调用，使用可计数 simulator 与合成秘密执行 AC-01 至 AC-06。

**验收场景**：AC-01、AC-02 为正常/拒绝主路径；AC-03 至 AC-06 覆盖隔离、配额与撤销竞争。

#### 用户故事 US-05 — 安装、取消与故障后保留控制（优先级：P1）

操作者安装/升级插件并能在失败、撤销、取消或重启后识别当前有效版本、实际结果与尚未证实的状态。


**为何此优先级**：安装和恢复不能扩大权限或重复执行副作用。

**独立测试**：以固定测试包、合成副作用 provider 和可信持久存储注入中断；无需真机。

**验收场景**：AC-07 至 AC-10、AC-12、AC-13。

#### 用户故事 US-04 — 设备中立的 Scene 与能力发现（优先级：P2）

开发者使用同一 core、Skill、Scene 状态和 action 装配不同设备/显示 profile；缺少能力时得到明确不兼容或已实现降级。


**为何此优先级**：避免第一设备细节成为核心必需依赖，支撑后续 adapter 接入。

**独立测试**：reference simulator 的 video/web/缺能力 profile，无须第二台真机。

**验收场景**：AC-11、AC-14；这些模拟 profile 不构成真实 Web 或第二机器人支持声明。

#### 用户故事 US-03 — T1 本体原屏交互（优先级：P2）

操作者在固定位置的 T1 本体打开动态内容，以语音和已验证机身触摸切页，再退出交回原厂显示。


**为何此优先级**：实现已确认首设备体验，必须建立真实显示与输入证据。

**独立测试**：在具备授权、已记录基线的 T1 上，用公开/合成内容完成输入、播放、恢复及原厂共存步骤。

**验收场景**：AC-16 至 AC-20 的 T1 部分；设备未到场时不伪造结果。

#### 用户故事 US-06 — 凭据不进入插件的业务扩展（优先级：P2）

操作者授予有限读取能力，应用通过可信 broker 获取允许的数据，插件看不到真实外部凭据。


**为何此优先级**：复用外部工具的同时保持账号权限边界；与首增量分开验证。

**独立测试**：用合成凭据和 Mock API 验证允许/拒绝、空数据、离线与刷新。

**验收场景**：AC-15；不声称真实 Lark OAuth、scope 或模型外传路径已通过。

#### 边界情况与体验约束

- 权限未授予、策略读取失败、运行时不合格、能力缺失、版本不兼容：在副作用前返回可识别原因和允许的恢复动作；不把“重试”作为默认批准或权限扩大。
- 空数据是成功的空结果；忙/排队/渲染中、离线、失败、拒绝和 unknown 各有结构化状态，供未来 CLI/界面呈现；不发明本轮并不存在的用户界面。
- action 只对当前前台应用生效；过期/重复输入、焦点变化、事件 gap 与背压必须有可观察处理，不靠输入重放续跑旧副作用。
- T1 初期视觉卡片不依赖精确音画同步；语音/触摸表达的是同一语义 action。物理输入种类按实际能力，不假设触摸屏、头触摸或多击可用。
- 这次是内部运行时规格复核，没有新增页面/导航设计；按包内原型选择策略不重建原型。既有离线显示 POC 仅是研究参考，不是产品原型确认或 Linux/T1 验收。未来真正新增应用 UI 时再在相关有界任务中确定视觉、可访问性与原型需求。

- 一套设备中立的能力发现、调用、任务结果、取消、事件、Artifact 与 Scene 契约；受监督的插件实例身份和独立 grant。

##### 身份、授权与隔离

1. 可信执行边界以实际受监督实例确定调用者；参数、Skill 文本、MCP 描述、模型输出或页面 action 不能指定更高权限主体。
2. Grant 只能由经独立认证的操作者通过 PolicyAuthority 创建/撤销；安装、签名、OAuth scope 和可猜到的 grant ID 均不是授权证明。实际权限取所有适用策略的交集；无明确允许、显式拒绝、冲突/不可识别策略或策略读取失败均拒绝。每次真实操作都在可信侧校验 grant、资源范围、schema、版本、有效期/epoch 与资源约束；入口 hook 或插件本地 allowlist 不能代替执行边界校验。
3. 默认不暴露宿主私有文件、其他插件数据、凭据存储、设备节点、厂家控制网络或容器管理 socket；默认不允许任意出网。代理环境变量不是网络隔离。
4. Build、安装脚本、MCP 和 renderer 均是不可信代码。构建环境无机器人/账号/模型凭据；renderer 无工具或 ConnectorBroker 能力。不同信任域不因资源紧张合并权限。
5. 最低隔离或能力要求不满足则拒绝相应任务；不静默降级隔离，也不擅自启用远端执行。
6. 撤销 grant 以可信权限服务提交的新策略代际为生效点；执行方在最终发送边界通过 PolicyAuthority 的 commitDispatch 再次校验。撤销/排队取消先于该提交点则不得签发执行权；提交点先发生则操作已in-flight，即使厂家调用尚不可见，不能承诺撤回。代理能力失效，运行实例收到终止请求；停止未证实则保留真实状态。撤销 qdroid grant 不冒充撤销第三方 OAuth 授权。
7. 使用预算、审批消耗、排队取消记录和对应dispatch意图由PolicyAuthority在同一admission事务中决定；并发不能超用，core缓存投影不是权限事实。unknown 不自动返还预算，同一已记录幂等请求不重复扣减；退款需要权威未执行证据和唯一审计调整，是否能重试仍由真实 provider 契约决定。

##### 执行、显示与恢复

1. 入队或厂家接受回执只能证明 `accepted`；`succeeded` 和停止证实需要该 provider 声明并实际提供的观察证据。
2. 超时/断连不能证明副作用未发生。commitDispatch持久记录意图后才可发送，commit与外部调用不是一个原子事务；两者之间崩溃也按可能已提交处理。PolicyAuthority拥有admission/budget/cancel事实；qdroidd拥有引用同一admission ID的Task状态投影，执行服务拥有厂家提交/观察证据。跨重启先查这些可信记录和可观察状态，不自动重发或续跑副作用。只有权威观察可用新状态版本解消unknown并保留旧证据；去重key与规范化输入冲突时拒绝。
3. 取消请求独立于任务终态；任务已完成与取消并发时保留实际观察结果，不能把一条取消回执改写为已停止。实例内全部任务进程的清理不能影响厂家或其他工作负载。
4. 设备资源由可信服务仲裁；插件不能指定任意原厂优先级。原厂告警/人工接管优先；不能以软件超时或控制源切换代替急停。
5. Scene 状态与输入 action 属于应用状态机。异步渲染、导入和播放请求绑定会话/显示代际与 revision；旧结果不能覆写新意图。宿主队列正确不代表厂家播放器已按同样顺序执行。
6. 产物完整校验后才能发布；渲染/导入失败保留经允许的旧画面或安全备用画面，不播放半文件。显示租期过期与协调器崩溃的恢复需由仍存活的可信组件执行并验证。
7. 未证明真实屏幕有界恢复前，仅展示公开或合成内容；不以循环播放敏感页面提供日程示例。不能保证的显示能力必须限制或标明不可用。
8. 排队取消与 commitDispatch 在同一admission权威内有可核对的先后关系：取消先生效则不得提交；提交先发生则只能按实际provider完成/取消/停止证据对账，不抹去可能已经发生的副作用。

##### 安装、版本与回滚

1. 安装前校验包根路径、文件类型/体积、固定版本、digest、目标平台、依赖与公共 API 主版本；拒绝路径逃逸、逃逸链接、设备文件和解压资源滥用。
2. 候选包先完成检查、无凭据构建/探测与权限差异检查，再激活。失败候选不改变当前有效版本，不启动其任务；清理候选临时资源并保留有界错误记录。
3. 运行任务固定其版本与实例身份；升级不原地替换运行中代码。新增权限不自动沿用旧 grant。
4. 升级失败保留/恢复上个合格版本供新任务使用；回滚不能恢复已撤销的 grant，也不能使旧实例绕过当前策略。已提交副作用按真实结果保留，不将包回滚解释为业务回滚。
5. 初始化协商协议/能力 schema 与限制；主版本不兼容、未知必需特性、未知授权/运行时字段、重复 JSON key 或无法满足的必需能力应可解释地拒绝。兼容版本的可选字段仅按其明确 schema 处理，不默默忽略授权相关语义；可选能力只按应用已实现的明确降级路径处理。
6. 同一 installation 的升级、回滚与移除串行化；激活/回滚按当前 generation 与 expectedActiveDigest 条件生效。过期候选失败不得覆盖后来已成功的版本，移除后的旧候选不能复活安装。
7. 不可变内容的清理尊重活动版本和运行任务引用；安装状态变更不能提前删除仍被任务使用的内容。私有状态按既定保留策略清理，不因此恢复grant。

#### 关键实体 *(功能涉及数据时包含)*

| 术语 | 产品含义 |
|---|---|
| Plugin package | 有版本、身份、声明、依赖与生命周期的扩展包；包类型不能自行提高信任级别 |
| Skill | 使用说明与资源；可包含不可信脚本，不等同于已安装依赖或已授予权限 |
| MCP server | 工具协议进程或远端服务；连接成功与工具的只读注解都不构成业务授权 |
| Manifest request | 插件申请的能力、资源与最低环境条件；不是 grant |
| Grant | 可信权限服务保存的、绑定主体/实例、操作、资源范围与有效期的授权 |
| Supervised instance | 可信 supervisor 创建并绑定身份的实际运行实例；不采信工具参数自报的主体 |
| Capability | 带版本、schema、范围、完成/取消语义与可用性证据的能力 |
| RobotAdapter | 将公共能力映射到厂家接口的受信实现；不得伪造厂家未提供的证据 |
| DisplayBackend | 把 Scene 呈现给用户的具体实现；通用契约不要求 MP4 |
| SandboxBackend | 执行并证明工作负载最低隔离属性、资源约束和清理行为的实现 |
| ConnectorBroker | 持有真实外部凭据并校验具体业务操作的可信服务 |
| Task / outcome | 一次调用及观察结果；接受、执行、完成、取消请求、停止证实与结果未知分别记录 |
| commitDispatch | 可信权限服务的原子执行接纳点；消耗预算、记录取消/审批检查及dispatch意图，不等于外部副作用已发生 |
| ArtifactRef | 受控产物引用；不接受插件指定任意宿主绝对路径作为可信产物 |
| Epoch / lease | 区分会话/服务重启的代际和执行有效期；执行端校验，跨节点不假定共享单调时钟 |
| Qualification | 在注明版本、环境与测试范围的条件下验证某实现满足要求；静态声明不等于资格验证 |

`RobotProfile` 记录设备能力与约束，`HostEnvironmentProfile` 记录主控特性与资源，`DeploymentProfile` 记录服务/板卡位置和受信链路。三者都不直接授予插件权限。配置声明、实际探测、测试证据、管理员策略和当前 grant 分开保存。

可信数据/证据的逻辑归属：

| 所有者 | 唯一负责的事实 | 工作负载限制 |
|---|---|---|
| PolicyAuthority | 操作者策略、grant/审批、撤销代际；admission ledger内的预算、取消标记与dispatch意图 | 仅提交请求；不能写grant、充当审批者或修改admission事实 |
| PluginSupervisor / 安装registry | 固定安装内容、实例身份与生命周期 | 不能自报替代实际实例、改安装记录或重分类为可信基础设施 |
| qdroidd / Task journal | Task ID、路由及结果投影、状态版本；引用权威admission ID | 仅按任务ACL查询；不能修改journal；其缓存不决定授权/取消竞争 |
| robotd / 执行journal | 执行端资源/lease/epoch、提交与设备观察证据 | 不能访问原厂控制接口或伪造执行结果 |
| DisplayCoordinator / player-agent | revision、显示所有权、提交队列与播放器侧恢复 | 提交Scene，不指定宿主路径/厂商优先级；不把提交当可见 |
| ConnectorBroker | 外部凭据、业务映射、刷新与下游结果 | 只使用受限代理；读取数据与对外披露分别检查 |
| ArtifactStore | 不可变产物、可信来源/归属、配额/保留 | ID不是授权；不能自证provenance或读其他实例产物 |

可信所有者可以按受控接口共同部署，不能由共享root插件进程代替。MVP不要求真实对外写操作；如果以后实现需审批效果，审批消耗与dispatch意图须由可信所有者原子记录，未知结果不重发。当前只在合成副作用/Mock API条件下验证对应恢复语义。

| EA-07 | 首 MVP 保持机器人固定位置，以显示、输入和有限观察能力验证链路；物理移动后续独立交付 | 不将运动能力开放作为本 Requirement 完成的必要条件；未来动作必须沿用安全契约 |
| EA-08 | 不承诺固定响应时间、内存/功耗数字或全部离线模型常驻 | 首轮主控实测后记录资源预算与可用规格；不得将桌面实验数字当机器人 SLA |

资源先验：

- 资源预算覆盖 core、可信服务、原厂常驻服务、工具与 renderer，而非只计算应用进程。
- EA-03 的并发是首期草案；每个活动任务必须有实际可执行的有限配额。低内存时可排队/拒绝或使用已验证的较小显示规格，不能共享凭据或取消隔离。
- Harness 本体运行不表示模型权重本地运行；模型、ASR/TTS 的位置、供应商与离线预算独立记录。没有授权时使用确定性驱动/fixture，不产生真实 API 消耗。
- 单机不排除 T1 内部多板结构。执行身份、epoch、文件转移、显示所有者与恢复责任必须落到具体节点，不能假设两块板上的 loopback/路径相同。

## 发布后观察计划（SDLC 补充）

每项运行证据至少说明：测试用例/AC、实际命令或可重复步骤、结果与退出状态、代码/包/profile 版本、Linux 环境、是否真实设备/账号、观察范围与未覆盖项。执行进度只由 lifecycle state 管理；本文不另建运行状态库。

成功的最早观察是：用户可以看到一个固定插件在真实 Linux 隔离环境调用 simulator 的被授权能力成功，而同一实例的越权调用被可信执行服务拒绝，并可检查相应审计结果。这个结果足以展示核心增量，不代表整个 MVP 完成。

首设备成功观察另需：T1 本体运行、原屏动态内容、语音和机身触摸切页、原厂显示交回以及故障恢复的实际证据。真实设备未到场时保持待测，记录清楚阻断的 AC；模拟器、规范、桌面 HTML→MP4 实验和浏览器自身沙箱都不能证明 T1 支持或整个产品安全。

- **观察条目**：最早增量的允许/拒绝结果与审计完整性；后续安装/恢复失败；T1语音/触摸成功、过期输入、实际可见与恢复限制；资源超额/崩溃；不收集日程正文或真实秘密作为公共指标。
- **基线或未知原因**：`none`。尚无运行代码、Linux资格或T1使用；现有桌面媒体研究不能作为设备/安全基线。
- **目标或判断方式**：按SC-001至006与适用AC检查；一项越权成功、未经证实的完成/停止或隐私残留即记录缺陷并限制相关能力。失败率用于发现问题，不先虚构长期SLA。
- **观察窗口**：每个稳定增量首次复现及其首次实际试用至该增量验收；未来设备首支持版本还须包含完整故障/恢复矩阵。具体日历时长在实际试用安排时由操作者确定，当前未承诺上线日期。
- **负责人**：未来交付的主Agent/验证负责人记录证据；操作者提供实际试用反馈。没有任命或联系外部人员，也未创建后台监控。
- **反馈回流**：未达本Requirement范围的行为先修复并保留证据；改变绑定产品行为或新增设备/外部效果时由主Agent更新/新建Requirement，保持原结果与变更来源。
- **确认来源/关联决定**：C-02、C-04至08。观察方法是对已确认结果的验证安排，非新增用户承诺。
